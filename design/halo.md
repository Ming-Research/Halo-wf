Decision: Halo is a Lua 5.1 engine written in Whitefoot with an embedding interface, its own package in `lib/halo` that firn binds, because Redis scripts are written against Lua 5.1 and firn's deployment needs `EVAL`, and an engine in Whitefoot keeps the script runtime under the language's guarantees ([purpose](../research/investigations/halo/DESIGN.md#purpose)), instead of embedding a native Lua engine through a host binding.

Decision: Halo's source never names Redis: firn supplies `redis.call`, `KEYS`, `ARGV`, the reply conversions, the `EVAL` error reply and the script cache, and names the chunk a script is compiled under, in which Halo locates its errors, and the codecs Redis scripts use live as general packages in `lib/json` and `lib/msgpack`, bound by Halo's `cjson` and `cmsgpack` libraries, because the engine and the codecs are to stand as projects of their own apart from firn, instead of an interpreter specialized to Redis.

Decision: Halo's replies are judged against Redis 7.0.15's bundled Lua 5.1 built on x86-64 Linux with glibc, because that is firn's reference platform and Redis's replies differ by platform where C leaves the result to the hardware and C library (`tostring(0/0)` is `-nan` there and `nan` on macOS arm64, and `struct` packs a NaN integer as `0x8000000000000000`), instead of the macOS arm64 build the corpus was first recorded on ([oracle](../research/experiments/halo-oracle/README.md), [codec results](../research/experiments/halo-luacodecs/RESULTS.md)).

Decision: Halo provides the Lua 5.1 library that Redis 7.0.15's sandbox exposes except `loadstring` and `load`, `getfenv` and `setfenv`, `collectgarbage`, `gcinfo`, `newproxy` with its `__gc`, weak tables, `string.dump`, `string.gfind`, `table.foreachi` and `table.setn`, because among 2,700 files in 2,168 repositories that GitHub's code search found calling `redis.call`, scripts call `math.mod` (Ohm's save script) and `table.foreach` (Discourse's presence scripts) and none calls the others ([survey](../research/investigations/halo/SCRIPTS.md#result)), instead of the whole sandbox; an excluded function is reconsidered when a host reports a script that calls it.

Decision: Halo provides Lua 5.1's coroutine library (`create`, `resume`, `yield`, `status`, `wrap` and `running`) with Redis 7.0.15's replies and error texts, because the owner reopened its exclusion as an experiment (the survey found no script calling it), and Firn has since asked for it to match Redis's sandbox, to find what Whitefoot gives and lacks for several execution stacks swapped through one interpreter and traced by the collector and to close one gap between Halo's library and Redis's sandbox, on the condition that the comparisons recorded before measuring pass, and both passed: the 31 coroutine oracle scripts reply byte-identically with Redis 7.0.15 at budgets 1, 7 and 1000, ordinarily and under collector stress, and none of the eight halo-bench kernels, which call no coroutine, ran slower than main on the 14900K beyond its larger range plus the twin's difference ([results](../research/investigations/halo/COROUTINES.md#results)), instead of keeping coroutines excluded on the survey's evidence.

Rejected:
- A separately named Redis adapter module in Halo's package, holding the `EVAL` error reply that firn and Halo's test host share: rejected because it puts Redis's reply format back into the engine's package and ties the engine to firn's protocol, while the host composes that reply from the embedding interface's error value and error line.
