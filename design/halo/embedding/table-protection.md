Decision: The embedding interface gives a host three general functions, one that sets or clears a table's metatable, one that reads a value's metatable, the shared string metatable for a string, and one that marks a table read-only for good, while host writes through the embedding still reach a read-only table, and the host decides which tables to protect, because Halo's source never names Redis ([Halo](../../halo.md)), Redis changes which tables it protects between releases (7.0.15 leaves the string metatable writable and 7.2.16 makes it read-only, [7.2.16 differences](../../../research/investigations/halo/REDIS-72.md#known-differences)), and a host that wrote a table's metatable and read-only fields itself would depend on Halo's table layout, instead of one function that applies Redis's protection rules or hosts writing those fields directly.

Rejected:
- One embedding function that applies Redis's protection, the globals table and the string metatable: rejected because it puts Redis's sandbox rules into Halo's source, and the function would change whenever a Redis release changes the protected set, as 7.2.16 did.
- Hosts writing a table's metatable and read-only fields directly, as the test host did: rejected because every host would then depend on Halo's table layout, which no interface contract covers.
