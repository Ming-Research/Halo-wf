Decision: A runtime type error names its operand as Lua 5.1's `getobjname` does (`local`, `global`, `field`, `upvalue`, `method`, or no name), found only when the error is raised by walking the faulting prototype's cells up to the faulting cell with the rules of `symbexec`, because the description depends only on the code before the faulting instruction and the handlers then change only by passing their operand's register to the slow executor, instead of computing a description for every instruction that can fail when the script is compiled, which repeats the walk for each such instruction, because the jump rule depends on the faulting position, and stores text that almost no run reads.

Decision: The walk reads Halo's own cells, with a fused compare or test applying its absorbed jump and a closure skipping its capture cells, because the cells carry every operand the walk reads and assembly's cell map keeps the instruction order that `symbexec`'s forward-jump rule compares, instead of a second copy of Lua's 32-bit instruction words kept only for the error path.

Decision: Each prototype's local-variable ranges, recorded by the compiler as `lparser.c` records them and converted to cell indexes, and its upvalue names are kept in the script as bytes outside the Lua heap, because the collector, its roots and its memory accounting then stay as they are, instead of heap string handles, which would add roots that the removed-root controls would also have to cover.

Decision: Argument errors name the called function as Lua 5.1's `getfuncname` does at the caller's call cell through the same `getobjname` walk used for operand descriptions, applying method argument adjustment and the unknown-name fallback, because aliases, fields, methods and shared builtins such as `math.mod` must produce the reference's names and argument numbers, instead of fixed names per builtin, which differ from Redis in those cases.
