Decision: A runtime type error names its operand as Lua 5.1's `getobjname` does (`local`, `global`, `field`, `upvalue`, `method`, or no name), found only when the error is raised by walking the faulting prototype's cells up to the faulting cell with the rules of `symbexec`, because the description depends only on the code before the faulting instruction and the handlers then change only by passing their operand's register to the slow executor, instead of computing a description for every instruction that can fail when the script is compiled, which repeats the walk for each such instruction, because the jump rule depends on the faulting position, and stores text that almost no run reads.

Decision: The walk reads Halo's own cells, with a fused compare or test applying its absorbed jump and a closure skipping its capture cells, because the cells carry every operand the walk reads and assembly's cell map keeps the instruction order that `symbexec`'s forward-jump rule compares, instead of a second copy of Lua's 32-bit instruction words kept only for the error path.

Decision: Each prototype's local-variable ranges, recorded by the compiler as `lparser.c` records them and converted to cell indexes, and its upvalue names are kept in the script as bytes outside the Lua heap, because the collector, its roots and its memory accounting then stay as they are, instead of heap string handles, which would add roots that the removed-root controls would also have to cover.

Decision: Argument errors name the called function as Lua 5.1's `getfuncname` does at the caller's call cell through the same `getobjname` walk used for operand descriptions, applying method argument adjustment and the unknown-name fallback; names and `luaL_error` locations share the immediate-caller rule, retaining the Lua caller for VM-invoked metamethods and generic-for iterators but leaving native-to-native calls unnamed and unlocated, because aliases, fields, methods and shared builtins such as `math.mod` must produce the reference's names and argument numbers and `luaL_where(L, 1)` inspects only the immediate caller, instead of fixed names per builtin or locating native errors at an outer Lua frame.

Decision: Only an error a native function raises as `luaL_error` takes its Lua caller's location; one it raises the way Lua raises its own runtime errors while that native function is the current call (the read-only refusal and a nil or NaN table key from the raw stores of `rawset`, `setmetatable` and the table and MessagePack libraries, and `next`'s invalid key) stays bare even when a script line calls it directly, while the VM's own table stores raise the same refusal located at their instruction; the raising body marks its error, and the location step that every base-library or library call returning an error passes through consumes the mark, so a mark never outlives its error, because `luaG_runerror`'s `addinfo` locates an error only when a Lua function is the current call (`lua_rawset`, `lua_rawseti`, `lua_setmetatable` and `luaH_next` raise with the C function current, `luaV_settable` with the script's function current), and a mark that outlived its error would turn a later `luaL_error` bare, instead of deciding the location from the message text or from a mark that other code must clear.

Rejected:
- Matching the message text, as the matcher of the nil and NaN key messages and the test host's read-only message did: rejected because the same text is raised located by a script's store and bare by `rawset`, so the text cannot decide, and each new message of this kind needed a new entry.
- A VM-wide mark cleared at each native call's entry and when a library resumes after a callback: rejected because a callback that catches a marked error under `pcall` returns into its library through neither point, so the library's own later `luaL_error` lost its location, as `table.sort`'s invalid order function error did after a comparator caught a `rawset` refusal.
- A separate unlocated variant of the raised outcome that native functions and host functions return: rejected because that type is public and every host constructs it while a host function's errors are never located, so the variant would mean nothing to hosts, and the table library's internal success flags would need a third state to tell a raw-store failure from its own `luaL_error`.
- Recording the raised error value and comparing it at the location step: rejected because strings are interned, so a later `luaL_error` with the same text would match a stale record.
