Decision: Halo grows a nonshrinking table array in place only after every failure point, building the new hash nodes and charging the byte difference before growing, initializing only the added suffix with nil and then placing integer keys from the old nodes into the array; shrinking keeps replacement, so the table still changes only on success, because with Whitefoot's `grow` lowered through reallocation (Whitefoot#280, release `wf-b2209fd31035`) growing in place made integer-table 12.0% faster on the 14900K with no kernel slower beyond its noise bounds ([result](../../../../research/experiments/halo-bench/RESULTS.md#growing-the-array-in-place-on-the-main-release)), table growth having taken about 30% of its inclusive samples ([profile](../../../../research/experiments/halo-bench/RESULTS.md#the-share-of-table-growth-on-the-14900k)), instead of allocating a replacement array and copying the retained prefix when the array does not shrink. Retain Lua's size selection and old-array-tail then reverse-old-node reinsertion order; reopen when another host or workload changes the comparison.

Decision: Halo retains power-of-two occupancy counting and initializes only the added array suffix, because [six full-LTO pairs](../../../../research/experiments/halo-bench/RESULTS.md#six-pair-table-growth-result) improve the ten-million integer-table kernel by 25.70% with no regression beyond the fixed noise guard, while [ordinary, stress and unsorted comparisons](../../../../research/experiments/halo-bench/RESULTS.md#table-behavior-and-selection) retain replies, borders and observed iteration order, instead of classifying every array index as a numeric key and reinserting the entire array through general insertion.
