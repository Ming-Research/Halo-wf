Decision: Lua-to-Lua calls, `__call`, `pcall`, `error` and host calls use the VM's own value stack and frame records, never the machine stack, while Lua code that the slow executor or a library function calls back (a `table.sort` comparator, `__tostring`, metamethods reached from the slow path) runs as a nested activation refused with "C stack overflow" at PUC's limit of 200, because script call depth then costs no machine stack and a script that reaches the callback limit gets Redis's error ([VM design, calls](../../research/investigations/halo/VM.md#3-calls)), instead of recursing on the machine stack for every Lua call. The machine stack that 200 nested activations use is unmeasured; this is provisional until it is (VM design, open ruling H2).

Decision: `table.sort` without a comparator, over elements `1..n` that all lie in the array part and are all numbers or all strings, sorts them in place synchronously by the steps of PUC's `auxsort` (same pivots, comparisons, swaps, bounds errors and smaller-half recursion, so the permutation is PUC's), while a comparator or any other case runs the resumable state machine whose comparisons can call back and be suspended, because the default comparison of such values calls no Lua and cannot suspend, and the state machine's frames and result slots made the sort kernel 2.8 times slower on the 14900K ([synchronous default sort](../../research/experiments/halo-bench/RESULTS.md#synchronous-default-sort)), instead of running every sort as the state machine.

Decision: `Call` and `TailCall` enter a live closure whose callee is a Lua prototype directly through the Lua frame setup, followed, when a coroutine is running, by the same charge of its stack growth the general call preparation makes, and send every other callee (native functions, closures bound to a native, `coroutine.wrap` functions, values called through `__call`, `pcall`, dead or invalid handles) through the general preparation, as PUC's `luaD_precall` separates a Lua function from everything else, because for a Lua callee the general preparation only re-reads the function slot, asks whether the closure is a `coroutine.wrap` function or has a native binding, calls the same frame setup and makes that charge, work that cost 94 of the 862.5 instructions Halo executed per call of fib before coroutines added the `coroutine.wrap` question and the charge ([entering a Lua callee directly](../../research/experiments/halo-bench/RESULTS.md#entering-a-lua-callee-directly-from-the-call-instructions)), instead of routing every call through the general preparation, or of entering directly only on the main thread, which costs the main thread the same one comparison of the running thread and leaves every Lua call inside a coroutine on the general path. Provisional: kept only if that section's criterion holds on the 14900K (fib at least 3% faster beyond its noise, no other kernel slower beyond its noise), measured again on the revision that adds the coroutine charge; a failed criterion removes this decision with the change.
